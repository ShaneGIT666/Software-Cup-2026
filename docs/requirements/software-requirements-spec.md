## 1. 引言

### 1.1 编写目的

本文档定义"基于多模态大模型技术的设备检修知识检索与作业系统"的功能需求和非功能需求，作为后续系统设计、开发实现和测试验收的依据。

本文档的读者包括：
- 软件开发团队（理解需求范围和优先级）
- 指导教师和评审专家（评估需求完整性和合理性）
- 测试团队（编写测试用例的依据）

### 1.2 项目背景

#### 1.2.1 赛题背景

本系统为第十五届中国软件杯大赛 A 组赛题"基于多模态大模型技术的设备检修知识检索与作业系统"的参赛作品。赛题由龙芯中科技术股份有限公司出题，要求采用 B/S 架构，部署在自主指令系统 LoongArch 架构加银河麒麟高级服务器版操作系统上运行。

#### 1.2.2 业务痛点

在钢铁、汽车制造等行业，大型企业产线设备密集且联动性强，传统运维面临以下核心痛点：

1. **知识分散形成"数据孤岛"**：检修知识分散于手册、日志与老员工经验中，缺乏统一的检索入口。
2. **新人上手慢**：经验丰富的检修人员退休或离职后，知识无法有效传承，新员工需要长时间学习。
3. **非计划停机损失巨大**：单次非计划停机损失超百万元，亟需快速故障诊断和标准化作业指引。
4. **作业不规范**：缺乏标准化的检修流程指引，操作依赖个人经验，存在安全隐患。

#### 1.2.3 解决思路

本系统以多模态大模型技术为核心支撑，整合多模态检修资源，实现以下目标：
- 快速检索检修方案和历史案例
- 提供标准化步骤化作业指引
- 支持知识数字化沉淀与高效复用
- 辅助一线人员诊断故障

## 2. 系统概述

### 2.1 系统目标

本系统旨在构建一套面向工业设备检修场景的智能知识工作台，核心目标包括：

1. **多模态知识检索**：支持文本、设备型号、故障描述等多种输入方式，实现精准语义检索与跨模态匹配，快速调取检修手册、历史案例和入库资料。
2. **标准化作业指引**：嵌入检修全流程，提供步骤化操作指引、合规校验提醒和安全注意事项，支持根据设备类型与检修等级个性化推送流程。
3. **知识沉淀与更新**：支持一线人员上传检修案例和经验总结，经审核后纳入知识库，实现知识实时更新和持续复用。
4. **大模型辅助诊断**：基于检索结果构建上下文，通过大语言模型生成带引用的诊断建议和作业提醒。

### 2.2 用户角色

| 角色 | 职责 | 核心操作 |
|------|------|----------|
| 一线检修人员 | 使用系统查找检修方案、记录维修经验 | 检索知识、查看作业流程、提交维修案例、上传现场材料 |
| 知识管理员 | 审核维修案例、管理知识资料 | 审核案例、上传和管理检修资料、标注修正大模型输出结果 |
| 系统管理员 | 部署和维护系统运行 | 配置 LLM 模型、管理运行环境、监控系统状态 |

### 2.3 运行环境约束

### 2.4 产品范围

#### 2.4.1 当前已完成范围

- 知识检索（关键词匹配 + 来源引用解释）
- 标准化作业流程查看
- 维修案例提交与审核
- 资料入库管理（PDF/TXT/Markdown/Office 文档/图片，解析结果进入 `pending_review`）

- 现场材料上传（图片/PDF）
- Chroma 向量检索可选增强（仅同步已审核资料片段，失败时回退关键词）

#### 2.4.2 二阶段规划范围

- 完整的权限管理系统
- 本地大模型部署方案

## 3. 功能性需求

### 3.1 多模态知识检索

#### 3.1.1 需求描述

用户输入设备型号、故障现象等文本信息，或上传故障图片，系统返回匹配的检修手册片段、历史维修案例和入库资料，并按相关性排序。

#### 3.1.2 功能要求

| 编号 | 功能项 | 描述 | 优先级 |
|------|--------|------|--------|
| FR-S01 | 文本检索输入 | 支持输入设备型号（文本）和故障现象（多行文本） | P0 |
| FR-S02 | 检索结果展示 | 返回按相关性排序的结果列表，每条结果包含标题、来源类型、来源名称、置信度、内容片段 | P0 |
| FR-S03 | 检索来源分类 | 结果按来源类型分为"手册""案例""资料"三类 | P0 |
| FR-S04 | 检索排序解释 | 每条结果展示命中词、来源位置（章节/页码）、排序分和字段级得分明细 | P1 |
| FR-S05 | 检索数量控制 | 支持配置返回结果数量（topK），范围 1-20 | P1 |
| FR-S06 | 图片输入检索 | 上传故障图片进行检索（二阶段规划） | P2 |
| FR-S07 | 语义向量检索 | 基于嵌入向量的语义相似度检索（二阶段规划） | P2 |

#### 3.1.3 当前实现说明

当前采用关键词匹配方案，通过分词后对设备型号和故障文本进行字段级加权匹配（标题权重 5、设备型号权重 4、标签权重 4、内容权重 2），结合来源类型基础权重（手册 3、案例 2、资料 2）和连续短语命中加分，实现 MVP 级可解释排序。已预留向量检索接口替换方案。

### 3.2 标准化作业指引

#### 3.2.1 需求描述

根据检索结果关联的设备类型和故障类型，展示标准化作业流程，包含步骤化操作指引、所需工具、安全提醒和验收标准。

#### 3.2.2 功能要求

| 编号 | 功能项 | 描述 | 优先级 |
|------|--------|------|--------|
| FR-W01 | 流程步骤展示 | 按顺序展示作业步骤，每步包含标题、描述、是否需校验、警告提示 | P0 |
| FR-W02 | 流程元信息 | 展示设备类型、故障类型、检修等级、所需工具 | P0 |
| FR-W03 | 安全提醒 | 展示作业安全注意事项 | P0 |
| FR-W04 | 验收标准 | 展示作业完成后的验收检查项 | P1 |
| FR-W05 | 个性化流程推送 | 根据设备类型与检修等级自动匹配对应流程（二阶段规划） | P2 |

#### 3.2.3 当前实现说明

当前通过检索结果中携带的 `workflowId` 关联作业流程，系统内置 3 条流程模板（启动困难、排气异常、异响检查），每条流程包含安全确认、检查步骤、复测和验收标准。新建案例默认绑定 `wf-001`，多故障类型扩展需要改为可推断流程匹配。

### 3.3 知识沉淀与更新

#### 3.3.1 需求描述

支持一线检修人员提交维修经验案例，经知识管理员审核后纳入知识库。支持上传检修手册等资料并自动解析为知识片段。支持手动标注与修正大模型输出结果。

#### 3.3.2 功能要求

| 编号 | 功能项 | 描述 | 优先级 |
|------|--------|------|--------|
| FR-K01 | 案例提交 | 填写设备型号、故障现象、可能原因、处理方案、处理结果和标签，提交案例 | P0 |
| FR-K02 | 案例审核 | 知识管理员审核案例，支持通过/拒绝操作，审核通过后案例进入知识库 | P0 |
| FR-K03 | 审核后再检索 | 审核通过的案例可被后续检索命中 | P0 |
| FR-K04 | 资料入库 | 上传 PDF/TXT/Markdown、DOCX/PPTX/XLSX 和图片格式的检修资料，自动解析为待审核知识片段 | P0 |
| FR-K05 | 资料管理 | 查看入库资料列表、详情、chunk 片段，支持删除资料 | P0 |
| FR-K06 | 手动标注修正 | 对资料知识片段进行人工修正并记录 revision；统一审核动作仍需补齐 | P1 |
| FR-K07 | 知识图谱构建 | 抽取实体关系、构建图结构知识关联（二阶段规划） | P2 |

#### 3.3.3 当前实现说明

案例提交和审核闭环已完成：案例提交后状态为 `pending_review`，审核通过后变为 `approved`，再次检索可命中新案例。资料入库已接入 `parser_router` 与 `mineru_adapter`，PDF/DOCX/PPTX/XLSX 优先 MinerU，PDF 可 fallback 到 pypdf，TXT/Markdown 走纯文本解析，图片进入 OCR/多模态分析链路；自动解析和模型分析生成的知识片段默认 `review_status=pending_review`，审核通过前不参与正式检索、RAG citations 或 Chroma 同步。当前资料片段支持查看和人工修正 revision，统一 approve/reject 审核接口仍是下一阶段任务。

### 3.4 大模型辅助诊断

#### 3.4.1 需求描述

基于知识检索结果构建上下文，通过大语言模型生成带引用来源的诊断建议，辅助检修人员判断故障原因和排查方向。支持多种模型提供商的可替换接入和失败降级保障。

#### 3.4.2 功能要求

| 编号 | 功能项 | 描述 | 优先级 |
|------|--------|------|--------|
| FR-A01 | RAG 增强回答 | 基于检索上下文生成诊断回答，包含可能原因、建议动作和引用来源 | P0 |
| FR-A02 | 引用溯源 | 回答中引用具体的知识来源（手册/案例/资料），含章节页码 | P0 |
| FR-A03 | 多 Provider 支持 | 支持 Mock、OpenAI、Anthropic 三种 Provider，通过配置切换 | P1 |
| FR-A04 | 降级保障 | 模型调用失败或无密钥时自动降级到 Mock Provider，确保演示不断线 | P0 |
| FR-A05 | 多模态诊断 | 结合图片进行视觉诊断（二阶段规划） | P2 |
| FR-A06 | 本地模型部署 | 支持本地大模型服务部署（二阶段规划） | P2 |

#### 3.4.3 当前实现说明

RAG 流程为：检索 → 构建中文 System Prompt（含设备型号、故障现象和检索上下文）→ 调用 LLM 生成 → 附上引用来源（citations）。Mock Provider 基于检索结果生成模板化中文回答和推荐动作。OpenAI 和 Anthropic Provider 已实现接口适配，通过环境变量配置 API Key/Base URL/Model 即可接入，调用失败时自动回退到 Mock，保证演示不断线。

### 3.5 现场材料上传

#### 3.5.1 需求描述

支持检修人员上传现场图片、PDF 报告等材料，作为故障分析依据和后续知识入库的素材。

#### 3.5.2 功能要求

| 编号 | 功能项 | 描述 | 优先级 |
|------|--------|------|--------|
| FR-U01 | 文件上传 | 支持上传 JPG、PNG、WebP 图片和 PDF 文件 | P0 |
| FR-U02 | 上传校验 | 校验文件类型、大小（10MB 上限）、MIME 匹配和空文件 | P0 |
| FR-U03 | 上传状态反馈 | 展示上传结果，包括文件 ID、文件名和访问 URL | P1 |

| 异常流程 | 输入为空时系统提示"设备型号和故障现象不能同时为空" |
| 后置条件 | 检索结果展示在界面上 |

## 6. 数据需求

### 6.1 知识数据类型

| 数据类型 | 存储文件 | 关键字段 | 说明 |
|----------|----------|----------|------|
| 设备信息 | `devices.json` | id, type, model, name, manufacturer, tags | 检修目标设备的基础信息 |
| 检修手册 | `manuals.json` | id, title, deviceModel, chapter, page, content, sourceName, tags, workflowId | 手册中的知识和检查流程片段 |
| 维修案例 | `repair-cases.json` | id, deviceModel, faultTitle, faultText, possibleCauses, solution, result, status, tags, workflowId | 一线人员提交的维修经验 |
| 作业流程 | `workflows.json` | id, title, deviceType, faultType, level, tools, safetyNotes, steps[], acceptanceCriteria[] | 标准化检修作业步骤 |
| 入库资料 | `documents.json` | id, fileName, sourceName, status, chunkCount, parser | 外部上传资料的元数据 |
| 知识片段 | `document-chunks.json` | id, chunk_id, documentId, source_doc_id, title, sourceName, page, section, content, snippet, keywords, review_status, version | 入库资料拆分后的知识片段；默认 `pending_review`，只有 approved 参与检索 |

### 6.2 数据关系

```
Device (设备)
  ├── Manual (手册片段) ──── workflowId ──→ Workflow (作业流程)
  ├── RepairCase (案例) ──── workflowId ──→ Workflow (作业流程)
  └── KnowledgeDocument (入库资料)
        └── KnowledgeChunk (知识片段)
```

### 6.3 数据量级目标

| 阶段 | 手册 | 案例 | 入库资料 | 知识点片段 |
|------|------|------|----------|------------|
| MVP 演示 | 5 条 | 4 条 | 2-3 份 | 10-20 个 |
| 二阶段 | 50+ 条 | 100+ 条 | 20+ 份 | 500+ 个 |

## 7. 约束与假设

### 7.1 技术约束

| 编号 | 约束 | 来源 |
|------|------|------|
| TC-01 | 必须采用 B/S 架构 | 赛题要求 |
| TC-02 | 必须部署在 LoongArch 架构 + 银河麒麟高级服务器版上运行 | 赛题硬性要求 |
| TC-03 | CPU 四核、内存 8GB+、硬盘 256GB+ | 赛题最低配置 |
| TC-04 | 前端使用 Vue 3 + Element Plus + Vite | 团队技术选型 |
| TC-05 | 后端使用 Python FastAPI | 团队技术选型 |
| TC-06 | MVP 阶段使用 JSON 文件存储，不引入重型数据库 | 保持轻量和可演示性 |

### 7.2 假设条件

| 编号 | 假设 | 说明 |
|------|------|------|
| AS-01 | 系统以单用户或小团队演示为主 | MVP 阶段不要求高并发 |
| AS-02 | 龙芯云平台提供 LoongArch 远程虚拟机 | 大赛将于 5 月中旬提供 |
| AS-03 | 大模型 API 有网络访问权限 | 若无法联网则全部使用 Mock 降级 |
| AS-04 | 用户使用主流现代浏览器 | Chrome、Firefox、Edge 最新版 |
| AS-05 | 检修数据为中文 | 当前系统仅支持中文内容 |

### 7.3 二阶段规划依赖

以下功能在当前 MVP 版本中暂未实现，将在二阶段根据时间和环境条件选择性接入：

| 规划功能 | 依赖条件 | 风险 |
