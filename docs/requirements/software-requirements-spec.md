## 1. 文档目的

本文档定义轻量设备检修知识与作业辅助系统的业务范围、功能需求、质量属性、数据规则、安全边界和验收标准，作为产品设计、开发拆分、测试和试点验收的共同依据。

本文档描述的是目标产品，不表示仓库当前原型已经满足全部要求。需求状态定义如下：

| 状态 | 说明 |
| --- | --- |
| MUST | 基础版本上线前必须满足 |
| SHOULD | 建议在 1.x 阶段满足，可按试点约束延期 |
| MAY | 可选扩展，不影响基础版本验收 |

MUST/SHOULD/MAY 只表示需求优先级。实现进度必须使用以下独立状态，禁止把“文件已创建”“测试总数增加”或“离线 SQL 可生成”直接写成“功能已完成”：

| 实现状态 | 判定标准 |
| --- | --- |
| 未开始 | 尚无设计或代码 |
| 已设计 | 接口、边界和验收方式已记录，尚无可执行实现 |
| 代码已搭建 | 已有实现文件，但尚未完成全部验证，可能仍存在已知冲突 |
| 单元已验证 | 隔离测试通过，只证明被测函数/SQL 形态，不等价于接口或真实依赖可用 |
| 集成已验证 | 按声明的集成边界，在目标数据库、真实 HTTP/代理、浏览器、文件系统或 Provider 上通过约定场景；Mock、离线 SQL 和进程内 `TestClient` 不属于该层证据 |
| 已完成 | 对应需求的代码、迁移、接口、安全/并发测试和验收证据齐全，且无未关闭冲突 |

六级实现状态与其他标记必须分开：“原型代码存在”只是仓库资产限定语，“待改造”只是优先级限定语，“可选”只是范围限定语，均不能代替上表状态。需求文件和设计方案只有在达到“已完成”标准后才能把对应功能标为已完成。发现新冲突或验证缺口时必须降回实际状态，并通过新修改日志追加更正，不能依赖历史通过数维持完成结论。

历史比赛需求及交付材料保留在其他文档中，仅用于追溯，不作为目标产品的约束。

## 2. 产品定位与目标

### 2.1 产品定位

系统是面向单个企业、工厂或设备运维部门的轻量知识与检修辅助平台。系统统一管理检修资料、标准作业步骤、维修案例和人工修正，通过可追溯检索与大模型辅助，帮助检修人员更快定位相关依据并按规范完成作业准备和复核。

系统是决策辅助工具，不是设备控制系统，不直接执行启停、参数调整、拆装或任何现场动作。

### 2.2 业务目标

1. 为分散的手册、制度、案例和经验提供统一入口。
2. 保证正式建议只引用已审核、当前生效且有权限访问的知识。
3. 将现场经验和知识修正纳入可审核、可追溯的版本闭环。
4. 在外部模型不可用时继续提供正式知识检索与标准流程查看。
5. 降低小型团队安装、运行、备份和恢复系统的成本。

### 2.3 成功指标

试点期应采集下列指标，具体基线由真实数据集确认：

- 核心检修查询的 Hit@5 和 Recall@5。
- 空检索结果比例。
- 未审核或无权限知识进入正式结果的次数，目标为 0。
- 检修人员找到可用依据的中位时间。
- 知识提交至审核完成的平均时间。
- 后台解析任务成功率和平均重试次数。
- LLM 降级时核心检索功能可用率。

上述指标用于试点建立基线，不直接作为 1.0 验收阈值；试点方案必须在采集前确定样本集、统计周期、责任人和目标值，经业务负责人批准后纳入后续版本验收。

## 3. 范围

### 3.1 基础版本范围

- 单企业、单实例和单一逻辑知识域。
- 基础版所有已认证业务用户共享同一知识域；只实施角色权限，不实施站点、班组或设备组级 ACL。
- 10–100 名注册用户，正常并发不超过 20 个交互请求。
- 数千份文档和数万级有效知识片段。
- 文本检索、图片线索、标准作业步骤和带证据智能建议。
- 资料、知识版本、维修案例和回答修正的审核闭环。
- 本地账户或企业 OIDC 登录。
- Windows 默认生产部署；同一代码在 Windows 和 Ubuntu CI 通过验证。
- PostgreSQL、受控文件目录、单一后台 Worker 和单一向量后端。
- 备份、恢复、日志、健康检查和基础运行监控。

### 3.2 范围外

- 多租户 SaaS 和复杂组织计费。
- 多地域主动—主动部署和跨数据中心一致性。
- Kubernetes、微服务和事件流平台作为基础依赖。
- 移动原生 App 和离线移动客户端。
- 站点、班组、设备组级数据隔离；若试点确认需要，应作为后续独立需求设计和验收。
- 完整工业知识图谱推理平台。
- 自动生成或批准作业票。
- 通过模型直接控制设备或自动执行检修操作。
- 替代法定安全制度、原厂手册或专业人员签字。

## 4. 用户、角色与权限

### 4.1 角色

| 角色 | 主要职责 |
| --- | --- |
| 检修人员 | 查询知识、查看作业步骤、提交现场经验和反馈 |
| 审核人员 | 审核知识版本、维修案例和回答修正，填写审核意见 |
| 知识管理员 | 上传资料、维护元数据、创建修订、废弃或替换知识 |
| 系统管理员 | 管理用户、角色、Provider、备份和运行配置 |
| 审计查看者 | 只读查看审核、权限和配置变更记录，可由管理员兼任 |

基础权限矩阵：

| 对象/操作 | 检修人员 | 审核人员 | 知识管理员 | 系统管理员 | 审计查看者 |
| --- | --- | --- | --- | --- | --- |
| 查询有效知识和流程 | 允许 | 允许 | 允许 | 默认禁止；需叠加业务角色 | 默认禁止；需叠加检修人员角色 |
| 提交案例或回答反馈 | 允许 | 禁止 | 禁止 | 默认禁止 | 禁止 |
| 上传资料、创建知识/流程修订 | 禁止 | 禁止 | 允许 | 默认禁止 | 禁止 |
| 审核知识、流程、案例和反馈 | 禁止 | 允许 | 禁止 | 禁止 | 禁止；仅可查对应审计事件 |
| 废弃/替换有效内容 | 禁止 | 审核决定 | 发起申请 | 禁止 | 禁止；仅可查对应审计事件 |
| 管理用户、角色和 Provider 元数据 | 禁止 | 禁止 | 禁止 | 允许 | 只读查看审计 |
| 执行服务器备份/恢复 | 禁止 | 禁止 | 禁止 | 仅经服务器运维授权 | 只读查看审计 |

同一用户拥有多个角色时权限取并集，但显式禁止和职责分离规则优先；前端显示不构成授权，后端必须逐项校验。

### 4.2 权限原则

- AUTH-01 MUST：除存活/就绪健康检查，以及当前启用认证模式的匿名登录入口（本地账户登录，或 OIDC 登录发起与授权回调）外，所有业务接口必须要求认证。匿名例外仅能用于建立身份，不得读取业务数据、下载附件或执行业务状态变更。
- AUTH-02 MUST：写操作必须由后端依据用户身份和角色授权，不能信任前端传入的 reviewer。
- AUTH-03 MUST：基础版在单一共享知识域中运行；检索、文档、附件和审核事件都必须先认证并执行相同的状态与角色权限检查。
- AUTH-04 MUST：审核人不得审核自己提交的知识版本。少于两名合格审核人的部署不得上线审核发布功能；基础版不提供绕过该规则的配置例外。
- AUTH-05 MUST：系统管理员默认不具备内容审核权；若同一自然人同时被授予两种角色，仍受“不得自审”和审计规则约束。
- AUTH-06 SHOULD：支持本地账户与 OIDC 两种认证模式，但一次部署只启用经管理员选择的模式。
- AUTH-07 MUST：本地账户密码采用成熟密码哈希算法保存，禁止明文或可逆加密。
- AUTH-08 MUST：会话过期、账号禁用和角色变更应及时生效。
- AUTH-09 MUST：审计查看者基线权限只能读取脱敏后的审计事件和运行报告，不能读取业务知识、流程、密钥，不能修改配置、作出审核决定或下载原始附件。确需读取业务知识和流程时，必须由管理员额外授予检修人员角色，权限叠加和访问行为都应写入审计。
- AUTH-10 MUST：所有建立或使用 Cookie 会话的浏览器写请求必须验证 `Origin`（必要时使用受控 `Referer` 回退）属于服务端可信来源；匿名登录也必须执行该检查，已登录状态变更还必须校验与会话绑定的 CSRF token。CORS 响应策略不得被当作服务端授权或防 CSRF 校验的替代品。
- AUTH-11 MUST：登录限流和安全审计使用的客户端地址必须由服务端统一解析。默认只信任直接连接地址；仅当直接上游位于显式配置的可信代理范围内时才能解析标准代理头，禁止业务路由直接信任客户端提供的 `X-Forwarded-For`。
- AUTH-12 MUST：密码哈希验证不得持有长事务或数据库行锁；验证成功后，签发会话前必须在写事务中重新校验账号仍启用、未删除、密码凭据未变化且 `auth_version` 一致，避免并发禁用、改密或角色安全变更后仍创建有效会话。

## 5. 核心业务规则

### 5.1 知识可信状态

知识版本状态至少包括：

```text
draft -> pending_review -> effective
                         -> rejected
effective -> superseded / deprecated
```

- BR-01 MUST：正式检索只返回当前 `effective` 版本。
- BR-02 MUST：自动解析、OCR、多模态分析、用户提交和人工修订不得直接成为 `effective`。
- BR-03 MUST：修改已生效知识时创建新版本，旧版本在新版本生效前继续提供服务。
- BR-04 MUST：审核“通过”即在同一事务中把新版本切换为 `effective`、把旧版本切换为 `superseded` 并产生索引更新事件；基础版不保留独立 `approved` 停留态。
- BR-05 MUST：拒绝、废弃和替换必须填写原因。
- BR-06 MUST：任何版本均应保留来源文件、页码/章节、提交人、审核人、时间和差异信息。
- BR-06A MUST：同一知识项在任一时刻最多存在一个 `effective` 版本，并由数据库约束或等价事务不变量保证。
- BR-06B MUST：废弃、替换或删除有效内容属于发布变更，必须由知识管理员发起、审核人员批准，不得由单一角色直接生效。

### 5.2 智能建议边界

- BR-07 MUST：智能建议只能使用调用者有权访问的有效知识作为正式证据。
- BR-08 MUST：模型生成内容与最终结构化回答必须来自同一次规则处理后的最终版本。
- BR-09 MUST：证据不足、关键参数缺失或存在高风险时，系统不得输出无条件确定结论。
- BR-10 MUST：图片识别结果在审核前只能作为查询线索，不能冒充正式证据。
- BR-11 MUST：生产环境不得加载开发样例作为正式知识，也不得使用 mock Provider 生成诊断、回答、OCR 或视觉观察。Provider 不可用时只能返回有效知识检索、确定性证据模板或明确的不可用提示；固定模拟内容不得进入 query、evidence、index 或审核对象。
- BR-12 MUST：智能建议不得触发设备控制或自动批准高风险操作。
- BR-13 MUST：“人工复核”指用户在执行现场操作前依据企业作业票、安全规程和授权链线下确认；本系统只显示复核要求，不替代或声称完成企业现场审批。若企业要求在系统中记录现场签署，应另行定义流程。

## 7. 数据需求

### 7.1 核心实体

目标数据库至少包含：

- User、Role、UserRole。
- Device、DeviceType。
- DocumentScopeMetadata（基础版仅保存适用信息，不作为 ACL）。
- Document、DocumentFile、DocumentParseTask。
- KnowledgeItem、KnowledgeVersion、KnowledgeSourceLocation。
- ReviewTask、ReviewDecision、AuditEvent。
- Workflow、WorkflowVersion、WorkflowStep。
- RepairCase、CaseAttachment。
- RagQuery、RagAnswer、EvidenceReference、RagFeedback。
- IndexJob、ProviderCallRecord、SystemSettingMetadata。

基础版设备型号和类型由知识管理员维护，支持界面增删改查及 UTF-8 CSV 导入；删除已被文档、知识、流程或案例引用的设备项时必须拒绝或改为停用。

### 7.2 数据一致性

- DATA-01 MUST：数据库是业务状态的唯一事实来源，向量索引和缓存是可重建派生数据。
- DATA-02 MUST：关键写操作使用事务。会改变可对外观察业务事实、并已登记下游消费者的领域写操作，必须在同一事务中追加版本化 outbox 事件；索引、缓存或异步任务更新由 outbox 或经批准的等价可靠机制触发。登录尝试、限流计数、会话签发/活动续期/注销、无下游事件契约的 bootstrap，以及 Worker 心跳/租约维护不发布业务 outbox。
- DATA-03 MUST：所有业务主键使用与操作系统和部署节点无关的稳定 ID。
- DATA-04 MUST：数据库保存 UTC 时间，界面按用户时区展示。
- DATA-05 MUST：删除受审计数据默认采用逻辑删除；物理删除遵循保留策略。
- DATA-06 MUST：上传文件、数据库记录和知识版本之间可双向追溯。
- DATA-07 MUST：迁移工具管理数据库版本，禁止生产环境手工改表替代迁移。
- DATA-08 MUST：认证、CSRF、权限等请求依赖不得提交或回滚调用方的业务事务；会话活动续期使用独立短事务。一次授权判断中的会话、用户版本和角色必须来自同一数据库一致性快照，避免角色变更与 `auth_version` 校验发生交叉读取。

## 8. API 需求

- API-01 MUST：目标接口基础路径为 `/api/v1`。
- API-02 MUST：接口返回稳定错误码、用户可读信息和 request ID。
- API-03 MUST：列表接口支持分页、排序和允许的过滤条件。
- API-04 MUST：创建、审核和任务重试等关键写操作支持幂等键或等价防重复机制。
- API-05 MUST：API 文档不暴露密钥、内部文件路径和堆栈信息。
- API-06 MUST：上传、下载和长任务接口设置明确的大小、超时和速率限制。
- API-07 SHOULD：旧 `/api` 在迁移期可保留，但必须有废弃计划和兼容测试。

## 10. 部署需求

### 10.1 Windows 默认部署

基础部署由以下部分组成：

- IIS 或 Caddy：HTTPS、反向代理和前端静态文件。
- FastAPI：独立 Windows Service。
- 后台 Worker：独立 Windows Service。
- PostgreSQL：Windows Service，可部署在同机或独立数据库服务器。
- 数据目录：位于代码目录之外的专用数据盘目录。

交付包自带前后端应用、迁移、Service 包装和运维脚本；客户预先提供受支持的 Windows、PostgreSQL 实例、HTTPS 证书及可选企业 Provider 地址。安装程序负责前置检查、应用服务注册、数据库迁移和受控数据目录初始化，不静默安装或修改客户的 PostgreSQL、IIS/Caddy、证书和企业身份系统。单机试点可使用明确记录版本的 PostgreSQL 安装包，但仍由管理员确认安装。

必须提供：

```text
install.ps1
upgrade.ps1
start.ps1
stop.ps1
backup.ps1
restore.ps1
diagnose.ps1
uninstall.ps1
```

安装和升级脚本必须可重复执行，失败时不得破坏现有数据库和文件。

### 10.2 Linux 部署

- MUST：同一代码、数据库模式和 API 在 Ubuntu CI 验证，平台差异不进入领域代码。
- MAY：提供 Linux 生产发行包；提供时 API 与 Worker 由 systemd 管理，平台脚本放在 `deploy/linux/`。
- MAY：提供 OCI 容器作为开发或 Linux 部署方式；它不是 Windows 基础部署前置条件。

## 11. 核心用例

### UC-01 检修人员查询故障

前置条件：用户已登录并有权访问目标设备知识。

主流程：

1. 输入或选择设备，填写故障现象和检修等级。
2. 若上传图片，系统先显示 OCR/视觉线索，用户确认、编辑或删除后再提交。
3. 系统执行认证、角色、状态和适用范围过滤后检索。
4. 用户查看结果、来源、版本和命中原因，并可选择或排除 RAG 证据。
5. 用户查看标准流程并按需生成智能建议。
6. 系统显示唯一最终回答、证据、不确定信息和人工复核要求。

异常流程：外部模型不可用时，系统显示降级信息，仍返回正式检索结果和流程。

### UC-02 知识管理员上传资料

1. 管理员选择文件并填写来源、设备和适用范围。
2. 系统校验文件、计算哈希并创建解析任务。
3. Worker 解析文件并生成待审核版本。
4. 管理员查看解析状态、来源位置和失败原因。
5. 内容进入审核列表，审核前不得被正式检索。

### UC-03 审核人员批准知识版本

1. 审核人员打开待审核版本及其来源和差异。
2. 审核人员通过或拒绝并填写意见。
3. 通过时系统事务性切换有效版本并写入审计/outbox。
4. Worker 更新索引；失败时任务可重试，旧索引不会被不可恢复地破坏。
5. 新查询命中新有效版本，旧版本保留历史追溯。

### UC-04 检修人员提交维修经验

1. 用户填写故障、原因、处理过程、结果和总结。
2. 系统保存为待审核案例。
3. 审核人员复核证据并作出决定。
4. 通过后案例作为正式知识来源参与检索。

### UC-05 管理员恢复系统

1. 管理员选择已验证的数据库与文件备份集。
2. 系统停止写入并执行恢复前检查。
3. 恢复数据库和文件，检查关联完整性。
4. 重建派生索引并执行核心烟测。
5. 输出恢复结果、RPO、RTO 和异常项。

## 12. 验收标准

基础版本必须满足以下门槛：

1. Windows 默认安装、升级、启动、停止和卸载流程在干净环境复验通过。
2. Ubuntu CI 验证通过，业务代码不存在固定盘符和用户路径；Linux 生产部署仅在被选为交付物时验收。
3. 本地账户或 OIDC 至少一种认证模式完成端到端验收。
4. 检修、审核、知识管理和系统管理角色的授权与越权测试通过。
5. 未审核、已废弃和无权限知识进入正式检索或 RAG 的违规数为 0。
6. 已生效知识的修订生成新版本并重新审核，不发生原地覆盖。
7. 文件无法通过静态目录访问；授权下载和审计记录正确。
8. Worker 在处理中重启后，任务能够恢复、重试或进入明确失败状态。
9. LLM、OCR 和向量服务分别故障时，系统按需求降级且不伪装成功。
10. 备份恢复演练成功，达到 RPO 24 小时、RTO 4 小时目标。
11. Windows 与 Ubuntu 自动化流水线通过后端单元/集成测试、前端类型检查与生产构建，以及检索—证据选择—RAG、上传—解析—审核—发布、角色越权三条核心 E2E；依赖必须由锁文件安装，任何跳过或失败均阻止发布。
12. 20 并发条件下达到规定的检索和普通 API 性能指标。
13. 检索评测报告记录数据集版本、配置、Hit@K、Recall@K、MRR、空结果和违规数。
14. 日志、错误响应和导出数据中不出现密钥、密码、令牌或服务器绝对路径。
15. 发布、废弃、替换或删除内容后，索引、轻量图谱和缓存均不返回旧的有效视图；索引更新故障时不出现新旧版本混合结果。
16. 生产模式下逐一断开 LLM、OCR、多模态和向量 Provider，系统不生成固定模拟线索或诊断，模拟内容进入查询、证据、索引和审核对象的数量为 0。
17. 审计查看者及四类业务角色的允许操作和越权请求均按权限矩阵验收。

### 14.2 并行开发前置条件

以下项目必须在 M1～M7 开始合并业务代码前冻结，并以版本化 OpenAPI/DTO 或 `contracts/` 文档维护。变更必须经过接口所有者评审，并在同一合并请求中更新消费者契约测试：

1. API 基础路径固定为 `/api/v1`；旧 `/api` 只维持兼容，禁止向旧接口新增生产功能。
2. 所有 v1 响应使用 `success`、`data`、`error`、`meta.requestId` 信封；错误使用稳定 `error.code`，不得把堆栈、密钥、绝对路径写入响应。
3. 身份上下文统一为 `CurrentUser` 依赖。业务请求不得再传入 `reviewer`、角色、用户 ID 或权限范围来决定服务端授权。
4. 分页统一采用 `limit` 与不透明 `cursor`；关键创建、审核、重试操作预留幂等键。其字段和错误码由 M0 维护。
5. 领域模块各自拥有表、Repository、迁移脚本与数据回滚说明；任何模块不得直接写入其他领域表。跨领域读取走只读服务接口或显式查询端口。
6. `main.py` 只负责中间件、异常处理和路由装配；除 M0 外的模块不得在其中直接新增业务逻辑。每个模块将路由注册到自己的 `api/v1/*.py`。
7. `data_store.py`、`knowledge.py`、`services.py`、`schemas.py` 与 `frontend/src/App.vue` 视为旧原型兼容层，除关键缺陷修复外不得继续堆叠新生产功能。
8. 所有生产写操作都必须按操作类型遵守事务和审计契约；M2/M3 中已登记下游消费者的关键领域写操作，在一个数据库事务内提交业务状态、审计事件、outbox 事件和接口要求的幂等记录。M1 安全状态变更与审计同事务，仅在已冻结版本化消费者契约时追加 outbox；认证维护、bootstrap 和 Worker 租约等不发布业务 outbox。M4 只消费 outbox，不直接修改 M2/M3 领域记录。
9. M2/M3 对外发布 `KnowledgePublished`、`KnowledgeRetired`、`WorkflowPublished`、`WorkflowRetired` 等版本化事件。事件至少包含 `eventId`、`aggregateType`、`aggregateId`、`versionId`、`occurredAt`、`requestId` 和不含密钥的 payload。
10. M5 只通过“授权后的有效知识/流程只读端口”获取上下文；M6 只通过 v1 API 与契约 Mock 访问后端，不导入后端内部模型。
11. M1 已在代码层关闭 DATA-08 身份事务/一致性门槛并交付认证路由，但真实 PostgreSQL 并发验收尚未完成；此前 M2/M3 仍只使用 `CurrentUser`/身份依赖 Mock。任何业务路由不得只因进程内测试通过就宣称已满足生产授权。
12. 任何模块只能按第 1 节实现状态定义报告进度；代码文件存在或单元测试通过时最多记录为“代码已搭建/单元已验证”。存在未关闭冲突、缺少真实依赖验证或接口闭环时禁止写“已完成”。
13. `/api/v1/health/ready` 的必需依赖策略归 M0 所有。领域 readiness 只返回脱敏健康状态，不得携带或降低 `required`；后续模块只新增自己的 contributor，不修改 `api/v1/system.py` 或另建健康聚合器。
14. 旧 `/api`、`/uploads`、`/knowledge` 的迁移期保护由 M0 `APP_LEGACY_SURFACE_MODE` 统一实施。M1～M5 不得逐路由复制 guard；生产只允许 `disabled`。应用层阻断不替代 M2 的受控下载/物理退役或 M7 的代理纵深防御。
15. M2/M3 写事务只使用 M0 `OutboxWriter` 和 M1 `AuditWriter` 公共端口；二者都不 commit/rollback 或返回 ORM。事件统一包含 `versionId`、`requestId`、`occurredAt`；M4 claim/lease 端口未冻结前不得直接导入 `OutboxEvent` ORM。

### 14.3 集成顺序与合并门槛

```text
M0 冻结契约/数据库基础
  ├─> M1 身份与审计 ───────────────┐
  ├─> M2 文档与知识版本 ──┐        ├─> M5 检索与 RAG
  ├─> M3 设备与作业流程 ──┼─> M4 ─┘
  ├─> M6 前端（使用契约 Mock）─────> 联调
  └─> M7 测试与运维（持续接入）─────> 发布验收
```

1. M0 完成并发布契约版本后，M1、M2、M3、M6、M7 可以同时开始；M5 可使用 M2/M3 的 Mock 端口并行实现。
2. M1 先发布稳定的 `CurrentUser` 与审计端口；关闭 DATA-08、AUTH-11、AUTH-12，通过认证路由和真实 PostgreSQL 集成测试后，M2/M3 才将后端生产写操作接入真实身份依赖。Windows Service、代理/备份恢复和 M6 浏览器 E2E 仍是产品发布门槛，但不阻塞已通过 PostgreSQL 验收后的后端领域接入。此前使用契约 Mock，不得自行实现第二套登录或权限判断。
3. M2/M3 冻结发布事件后，M4 接入真实 outbox；在此之前可用事件样例测试消费者，不得轮询或直接修改领域数据。
4. M2/M3 提供只读端口、M4 提供索引状态后，M5 切换 Mock 为真实依赖；M6 同步完成端到端联调。
5. 任一模块合并前必须满足：模块级单元测试、契约测试、数据库迁移可升级和可降级说明、无跨模块私有导入、`git diff --check` 通过。影响公开契约时必须同时更新 API 文档和消费者测试。
6. 每次代码、配置、迁移、脚本、测试或文档修改都必须在变更说明中标明所属模块（M0～M7）；跨模块修改必须列出主责模块和协作模块，禁止使用“通用修改”等无归属描述。
7. 每次变更说明必须至少包含：改动内容与原因、变更文件、对外 API/DTO/事件/数据库影响、依赖模块、冲突或重复实现检查结论、验证命令及结果、回滚方式。没有这些信息的变更不得合并。
8. 修改前必须检索现有实现、OpenAPI/DTO、迁移和需求追踪矩阵，确认不重复实现已有能力、不改变已发布契约语义、不与其他模块进行中的接口冲突；发现重叠时应复用既有模块或先提议契约变更。
9. 发布门槛除第 12 节验收标准外，还要求 M0～M7 的需求追踪矩阵均已关联实现、自动测试和验收证据；未完成的 MUST 不得标记为 1.0 可发布。

### 14.4 协作与冲突控制

- 每个模块使用独立分支、独立数据库迁移文件和独立测试文件；不允许多人同时修改同一个 Alembic revision。
- M0 维护迁移分支头；截至 2026-08-14 为 `20260814_0005`。其他模块提交迁移前必须先基于最新迁移头 rebase；出现多头时只由 M0 或指定集成人员合并，任何人不得修改已登记的 `0001`～`0005`。
- 公共 DTO、错误码、事件和 OpenAPI 版本由 M0 代码所有者维护；领域团队可提变更，但不得绕过评审直接修改已发布字段语义。
- 临时 Mock 必须放在测试或前端 mock 层，不得进入生产 Provider、正式检索、索引或审核链路。
- 任何模块发现需要修改其他模块私有目录时，应先增加接口/事件而非直接耦合；确有例外时需记录原因、所有者和拆除日期。

### 14.5 强制变更说明与本地修改日志

每次完成一个逻辑变更单元后，必须在 `docs/change-log/` 保存一份独立的 Markdown 记录，并在 `docs/change-log/INDEX.md` 登记。一个逻辑变更单元可以包含为实现同一目标而同时发生的代码、配置、迁移、测试、脚本和文档修改；日志文件自身、索引登记和模板维护不再递归产生额外日志。

后续开发开始前，开发人员或自动化代理必须先读取日志索引，并阅读与本次模块、公开契约、数据库迁移或待续事项相关的最近记录。历史记录只允许追加更正说明，不得静默重写；替代已有方案时，应新建记录并明确标记被替代的变更标识。没有本地日志记录和索引登记的修改不得合并。

提交、合并请求、交付记录或自动化代理的修改说明必须与对应本地日志使用相同的变更标识和以下模板。状态报告也应使用同一模板，以使后续开发人员能够判断是否存在重复调整或矛盾。模板文件位于 `docs/change-log/TEMPLATE.md`。

```text
变更标识：<日期/分支/提交或任务编号>
所属模块：M<主责模块>；协作模块：M<编号列表或无>
需求追踪：<FR/BR/DATA/API/NFR 编号>
本地日志：docs/change-log/<YYYY-MM-DD-NNN-简述>.md

改动内容：
- <新增、修改或删除的能力，以及原因>

文件与数据影响：
- <文件路径；新增/修改/删除>
- <数据库表、迁移、API、DTO、事件、配置项；无则明确写“无”>

依赖与冲突检查：
- 已检查：<已检索的模块、契约、迁移头和进行中工作>
- 结论：<复用/新增/替换原因；不存在重复或矛盾，或列出已协调事项>

验证与回滚：
- 验证：<命令、测试、结果>
- 回滚：<可逆方式、迁移降级或恢复步骤>

后续开发提示：
- <仍未解决的约束、下一次修改前必须读取的契约或不允许重复实现的内容；无则明确写“无”>
```

示例：M2 新增文档版本表时，应声明“所属模块 M2；协作模块 M0（迁移头）和 M1（当前用户）”，在 `docs/change-log/` 创建记录，列出新表、`KnowledgePublished` 事件和受影响 API；不得顺带修改 M5 的 RAG 过滤逻辑。若确需修改，应拆为另一条由 M5 主责的变更并通过契约联调。

## 15. 风险与待确认事项

| 项目 | 待确认内容 | 影响 |
| --- | --- | --- |
| 身份系统 | 本地账户、Microsoft Entra ID 或企业现有 OIDC | 登录、部署和离线能力 |
| 数据范围扩展 | 基础版为单一共享知识域；试点是否需要站点、设备组或班组 ACL | 后续权限和检索过滤模型 |
| 数据规模 | 实际文档数量、平均页数和年增长量 | 数据库、文件和向量选型 |
| 模型策略 | 云端、企业内网服务或本机模型 | 资源、合规和响应时间 |
| 文件策略 | 本地数据盘、NAS 或对象存储 | 备份、权限和跨平台部署 |
| 合规要求 | 是否适用等保、数据出境或行业专项制度 | 安全范围和项目周期 |
| 高风险定义 | 哪些设备、操作和风险等级必须双人复核 | 规则与审核流程 |
| 保留周期 | 文档、回答、审计和日志保留期限 | 存储和删除机制 |
| Linux 交付 | 是否除 Ubuntu CI 外正式交付 systemd/容器安装包 | 发布工件和运维范围 |

上述事项应在详细设计前由产品负责人、现场检修负责人、IT 运维和安全负责人共同确认。
