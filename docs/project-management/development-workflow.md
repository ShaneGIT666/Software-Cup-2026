## 1. 项目定位

本项目面向“基于多模态大模型技术的设备检修知识检索与作业系统”赛题，目标是在有限时间内完成一个可演示、可部署、文档完整的 B/S 系统原型。

系统优先覆盖以下核心能力：

1. 多模态知识检索：支持文本、设备型号、故障描述、图片等输入，返回检修资料、故障原因、处理建议。
2. 标准化作业指引：按设备类型、故障类型、检修等级生成步骤化作业流程，并包含安全与合规提示。
3. 知识沉淀更新：支持上传案例、经验总结、人工标注与审核入库。
4. 可视化演示界面：提供 PC Web 端，适合比赛答辩和功能演示。
5. 国产化部署说明：交付部署文档，说明如何适配 LoongArch 架构和银河麒麟高级服务器操作系统。

当前仓库状态为基础骨架阶段，仅包含目录结构，尚未确定最终技术栈和业务代码。

## 2. 推荐技术路线

为兼顾三人开发效率、比赛展示效果和国产化部署可行性，建议采用轻量 B/S 架构：

| 层级 | 推荐方案 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 或 React + TypeScript | 快速构建演示界面，适合组件化协作 |
| 后端 | Python FastAPI 或 Node.js NestJS/Express | 提供检索、文件上传、作业流程、模型调用 API |
| 数据库 | SQLite 开发期，PostgreSQL/MySQL 部署期可选 | 开发快，后续可平滑迁移 |
| 知识检索 | 本地向量库或轻量检索模块 | 初期可用文本检索模拟，后续接入 embedding |
| 大模型 | 云 API 优先，本地模型作为扩展 | 比赛初期优先保证演示稳定 |
| 文件存储 | 本地目录 `data/` | 存放手册、案例、上传文件 |
| 部署 | Docker 或手动部署脚本 | 输出部署文档，说明国产系统适配方式 |

技术栈在正式编码前由三人共同确认一次，确认后不得频繁更换。

## 4. 三人角色分工

三人都需要理解完整业务，但每个人有明确主责，避免重复开发和无人兜底。

### 成员 A：前端与产品体验负责人

主责：

1. 负责 `frontend/`。
2. 设计并实现 PC Web 主界面。
3. 完成多模态检索入口、检索结果页、作业指导页、知识提交页、审核管理页。
4. 维护页面交互流程、演示路径、空状态、错误状态、加载状态。
5. 参与编写产品说明书和演示 PPT。

关键交付：

1. 可运行的前端工程。
2. 主要页面原型和最终 UI。
3. 前后端接口联调结果。
4. 演示脚本中的用户操作流程。

验收标准：

1. 用户能从首页完成一次完整的“输入故障信息、查看检索结果、进入作业步骤、提交经验案例”流程。
2. 页面在常见桌面分辨率下无明显错位和文字重叠。
3. 异常提示清晰，演示时不会出现空白页。

### 成员 B：后端、检索与大模型负责人

主责：

1. 负责 `backend/`、`data/`、核心 API。
2. 设计知识文档、案例、设备、作业流程的数据结构。
3. 实现文本检索、设备型号检索、案例检索和模型调用适配。
4. 实现图片上传接口，并预留多模态模型或 OCR 接入位置。
5. 提供稳定 API 给前端联调。

关键交付：

1. 可运行的后端服务。
2. API 文档和接口示例。
3. 种子数据导入能力。
4. 检索和问答的最小可用闭环。

验收标准：

1. 前端可通过 API 获取检索结果、作业步骤和案例数据。
2. 后端在未配置真实大模型时能提供降级响应，保证演示不断线。
3. 数据结构能支撑手册、故障案例、审核状态和人工标注结果。

### 成员 C：测试、文档、部署与项目协调负责人

主责：

1. 负责 `docs/`、`deploy/`、`scripts/`、`tests/`。
2. 维护需求分析、设计文档、测试报告、部署文档。
3. 组织每周任务拆解、每日进度同步和版本验收。
4. 编写测试用例，覆盖核心演示路径。
5. 准备比赛提交材料，包括 PPT、演示视频脚本、安装部署说明。

关键交付：

1. 完整比赛文档包。
2. 部署手册和运行说明。
3. 测试用例与测试报告。
4. 版本发布清单和演示检查表。

验收标准：

1. 每个重要功能都有对应需求、设计、测试记录。
2. 新成员按部署文档可以在本地启动项目。
3. 比赛提交清单中的材料不缺项。

## 5. 阶段计划

### 阶段 0：立项与技术确认

目标：统一方向，避免后期返工。

任务：

1. 明确最终技术栈。
2. 确认核心演示场景：设备故障检索、标准作业指引、经验案例沉淀。
3. 确认设备类型和样例数据范围。
4. 建立任务看板和分支规则。

产出：

1. 技术选型记录。
2. 第一版需求清单。
3. 第一版页面草图。
4. 第一版数据结构草案。

### 阶段 1：最小可运行闭环

目标：先跑通端到端流程。

任务：

1. 前端完成基础页面和路由。
2. 后端完成健康检查、检索、作业步骤、案例提交 API。
3. 数据目录加入少量样例手册和故障案例。
4. 完成前后端联调。

产出：

1. 用户可打开 Web 页面。
2. 用户可提交故障描述并看到结果。
3. 用户可查看步骤化作业指导。
4. 用户可提交经验案例。

### 阶段 2：核心能力增强

目标：让系统更像“智能检修助手”，而不是普通查询页。

任务：

1. 接入大模型 API 或模拟模型服务。
2. 引入知识来源引用、置信度、相关设备、相关案例。
3. 增加图片上传入口和识别结果占位。
4. 增加人工审核、标注、修正流程。
5. 优化 UI 和演示体验。

产出：

1. 检索结果包含来源和解释。
2. 作业指引包含安全提醒和合规检查。
3. 知识沉淀流程可演示。
4. 有一条完整的高质量答辩演示路线。

### 阶段 3：测试、部署与文档完善

目标：满足比赛交付要求。

任务：

1. 完成需求分析文档。
2. 完成功能设计文档。
3. 完成产品说明书。
4. 完成功能测试报告。
5. 完成安装包和部署文档。
6. 录制 7 分钟以内演示视频。

产出：

1. 可提交源码。
2. 可运行安装包或部署包。
3. 完整文档包。
4. 演示 PPT 和演示视频。

## 7. 每日协作流程

建议采用轻量敏捷节奏：

1. 每天开始前 10 分钟同步：昨天完成什么、今天做什么、是否有阻塞。
2. 每天结束前 10 分钟同步：是否可运行、是否影响他人、是否需要联调。
3. 每个功能任务必须有关联 Issue 或任务编号。
4. 每人每天至少提交一次可说明目的的 commit。
5. 涉及接口、数据结构、路由路径的改动必须提前同步。
6. 每两到三天合并一次稳定版本到主分支。

## 8. Git 分支与提交规范

推荐分支：

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定分支，保持可运行 |
| `dev` | 日常集成分支 |
| `feature/FE-xx-name` | 前端功能分支 |
| `feature/BE-xx-name` | 后端功能分支 |
| `docs/DOC-xx-name` | 文档分支 |
| `fix/short-name` | 缺陷修复分支 |

提交信息格式：

```text
type(scope): summary
```

示例：

```text
feat(search): add basic retrieval api
feat(frontend): add search result page
docs(requirements): add first requirement draft
test(api): add retrieval api cases
fix(upload): handle empty file name
```

常用类型：

| 类型 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复问题 |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 重构 |
| `chore` | 工程配置 |
| `style` | 样式调整 |

## 9. Pull Request 规则

每个 PR 必须包含：

1. 本次改动内容。
2. 影响范围。
3. 自测结果。
4. 是否需要其他成员联调。
5. 截图或接口示例，前端和 API 改动必须提供。

合并要求：

1. 不允许直接向 `main` 推送功能代码。
2. 至少一名其他成员查看后合并。
3. 合并前确认项目能启动。
4. 接口变更必须同步更新文档。
5. 演示关键路径出现问题时优先修复，不继续堆新功能。

## 10. 接口协作约定

后端提供接口前，先输出接口草案：

```text
METHOD /api/path
请求参数
响应字段
错误码
示例响应
```

前端可以先基于 mock 数据开发，后端接口稳定后切换真实请求。

推荐首批接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/health` | 服务健康检查 |
| `POST /api/search` | 知识检索 |
| `POST /api/diagnosis` | 故障诊断建议 |
| `GET /api/workflows/:id` | 获取作业流程 |
| `POST /api/cases` | 提交经验案例 |
| `GET /api/cases` | 案例列表 |
| `PATCH /api/cases/:id/review` | 审核案例 |
| `POST /api/uploads` | 上传图片或文档 |

## 11. 测试策略

优先保证比赛演示路径稳定。

测试分层：

1. 单元测试：后端检索、数据处理、模型适配。
2. 接口测试：核心 API 请求和异常场景。
3. 前端自测：页面加载、表单校验、结果展示。
4. 端到端测试：完整用户演示路径。
5. 部署测试：按部署文档从零启动项目。

核心验收用例：

| 用例 | 预期结果 |
| --- | --- |
| 输入设备型号和故障描述 | 返回相关手册、案例和处理建议 |
| 上传故障图片 | 图片被保存，并返回识别或占位结果 |
| 查看作业指导 | 展示步骤、安全提醒、工具清单 |
| 提交经验案例 | 案例进入待审核状态 |
| 审核通过案例 | 案例进入知识库可检索范围 |
| 未配置模型密钥 | 系统给出降级提示，不崩溃 |

### 12.1 文档自包含规则

后续所有项目文档必须满足“上下文自包含”原则：接收者只 clone 仓库、不读取任何历史聊天记录，也能通过文档清晰理解当前开发进度、软件功能、风险边界和下一步任务。

每次新增或修改文档时，至少检查以下内容：

1. 是否说明当前功能已经做到什么、尚未做到什么、不能夸大为什么。
2. 是否列出与该文档相关的关键代码、接口、脚本、配置或数据文件。
3. 是否写明最近一次可信验证结果，例如测试命令、构建结果、真实 API 验收或未执行原因。
4. 是否说明后续开发者或 agent 的下一步动作，而不是只记录历史过程。
5. 是否避免依赖“如上所述”“见聊天记录”“之前已经说过”等脱离仓库后不可追溯的上下文。
6. 如果文档内容改变了 API、数据状态、部署方式、演示路径、风险口径或任务优先级，必须同步更新 `agent-startup-context.md` 和 `current-handoff.md`。

该规则优先适用于 README、Agent 初始化入口、交接文档、API 契约、测试报告、部署文档、演示 runbook 和任务计划；普通格式整理也不得破坏文档的自包含性。

## 13. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 大模型接入不稳定 | API 超时、额度不足、网络失败 | 后端提供降级响应和演示数据 |
| 多模态能力难度高 | 图片识别效果不可控 | 先做图片上传和结果占位，再接 OCR 或多模态模型 |
| 文档滞后 | 最后集中补文档质量差 | 每完成一个功能同步补需求、设计、测试记录 |
| 三人代码冲突 | 同时修改同一模块 | 明确目录负责人，接口变更先同步 |
| 国产环境适配不足 | 比赛部署环境无法直接运行 | 早期记录依赖版本，避免使用冷门系统依赖 |
| 演示路径不稳定 | 答辩时接口或数据异常 | 固定演示数据，准备离线降级模式 |

## 14. 近期优先事项

建议下一步按以下顺序推进：

1. 三人确认技术栈。
2. 建立 `dev` 分支和任务编号。
3. 成员 A 初始化前端工程。
4. 成员 B 初始化后端工程和首版 API 草案。
5. 成员 C 编写需求分析文档大纲和演示路径。
6. 三人共同确认第一批样例设备、故障案例和手册来源。
7. 三天内完成最小可运行闭环。

最小闭环完成前，禁止扩展过多非核心功能。优先确保“能打开、能搜索、能看步骤、能提交案例、能演示”。
