# 项目启动会流程

> [!WARNING]
> **历史快照（非现行基线）**：本文记录 2026 年前期竞赛原型、阶段调研、验证或交付准备，仅用于追溯当时事实。文内“当前”“最终”“正式”“已完成”“必须”“一键部署”等表述均限定于当时范围，不构成现行产品状态、开发顺序、生产要求或交付承诺。现行文档的适用范围和来源优先级只以[根 README](../../README.md)第 1 节为入口；需求语义、动态状态、公共契约、领域事件和变更证据分别遵循该节指向的唯一事实源。本文中的命令、测试数量和部署结论未经当前版本复验，不得作为当前验收证据。

建议正式开发前开一次 45 到 60 分钟启动会。会议目标不是泛聊，而是把开工需要的关键决策一次性定下来。

## 1. 会前准备

每位成员会前需要完成：

1. 阅读赛题说明。
2. 阅读 `docs/project-management/development-workflow.md`。
3. 准备自己能投入的时间段。
4. 准备自己倾向的技术栈和理由。
5. 准备一个认为最适合演示的设备检修场景。

## 2. 会议议程

| 时间 | 议题 | 产出 |
| --- | --- | --- |
| 5 分钟 | 明确比赛目标和提交物 | 统一目标 |
| 10 分钟 | 讨论系统 MVP | MVP 功能边界 |
| 10 分钟 | 确认设备与故障场景 | 第一批样例数据范围 |
| 10 分钟 | 确认技术栈 | 技术选型记录 |
| 10 分钟 | 确认三人分工 | A/B/C 职责与任务 |
| 10 分钟 | 确认近期计划 | 三天内最小闭环任务 |

## 3. 必须形成的决定

会议结束前必须明确：

1. 前端使用什么框架。
2. 后端使用什么框架。
3. 开发期数据库使用什么。
4. 大模型先接真实 API 还是先做模拟服务。
5. 第一批演示设备是什么。
6. 第一批演示故障有哪些。
7. 三天内要完成哪些最小闭环功能。
8. 每个人第一批任务是什么。

## 4. 推荐讨论结论

如果团队还没有明显偏好，建议采用以下默认结论：

| 决策项 | 推荐结论 | 原因 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript | 国内资料多，上手快，适合后台型系统 |
| 后端 | Python FastAPI | API 开发快，适合模型和检索能力接入 |
| 数据库 | SQLite | 开发期简单，便于演示和提交 |
| 大模型 | 先模拟服务，后接真实 API | 先保证演示闭环稳定 |
| 检索 | 先关键词检索，后向量检索 | 逐步增强，减少早期风险 |
| 设备场景 | 摩托车发动机检修 | 赛题给出参考手册，资料来源更自然 |

## 5. 会后行动

会议结束当天完成：

1. 更新 `technical-decision-record.md`。
2. 更新 `mvp-scope.md`。
3. 更新 `task-board.md`。
4. 建立 `dev` 分支。
5. 三人各自创建第一个功能分支。
