# 本地修改日志

本目录记录目标产品改造中的每一个逻辑变更单元，供后续开发、代码审查、联调和回滚时使用。它是仓库内的长期记录，不替代 Git 历史、提交说明或需求追踪矩阵。

## 使用规则

1. 开始修改前，先阅读 [INDEX.md](INDEX.md)，再阅读与本次主责模块、协作模块、API、DTO、事件、数据库迁移或待续事项相关的最近记录。
2. 完成一个逻辑变更单元后，立即复制 [TEMPLATE.md](TEMPLATE.md) 创建记录，文件命名为 `YYYY-MM-DD-NNN-简短主题.md`；同一次目标产生的代码、配置、迁移、测试、脚本和文档调整写入同一条记录。
3. 在 [INDEX.md](INDEX.md) 增加一行，记录变更标识、模块、状态、简述和日志链接。新记录按日期和序号递增排列。
4. 日志、索引和模板本身不递归触发新的日志记录。本目录的创建或规则变更应只登记一条对应的机制变更记录。
5. 记录状态为“变更已结束”的日志不得静默改写。需要纠正、回滚或替换时，新增一条日志并通过“关联记录”字段引用原变更标识；日志正文中的功能状态必须按其记录当时口径理解。
6. 每条状态声明必须填写“状态对象”，不能用某个端口或测试的证据代表整个模块；纯文档治理不得提升代码功能状态。仅文档治理仍使用六级功能状态时，该状态表示被治理的需求/契约当前最高证据，不表示文档编辑是否结束；编辑是否结束只看“记录状态”和验证段。
7. “规范来源影响”必须区分需求语义、动态状态、设计/领域事件和可执行契约：需求语义只改 SRS，动态状态只改当前追踪矩阵，所有设计与具体事件只原位修改[统一软件设计与后续开发方案](../design/follow-up-development-plan.md)，可执行契约按代码所有权同步维护；不得为后续变更新建设计文档文件。
8. 变更未产生代码或数据影响时，必须明确填写“无”；不要省略字段。任何跨模块变更必须标明主责和协作模块。

完整强制要求见 [软件需求规格说明书第 14.5 节](../requirements/software-requirements-spec.md#145-强制变更说明与本地修改日志)。
